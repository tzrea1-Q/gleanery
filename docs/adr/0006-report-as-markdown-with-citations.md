# 报告存为单篇 Markdown 加内部 ID 引用标记，不用结构化区块

报告的正文是一篇 GFM Markdown，含标题、表格、列表和引用块。引用原文时，在正文里写 `[[c:123]]`（内容）或 `[[m:456]]`（评论），用的都是内部 ID。保存时，后端解析出全部引用并逐个校验，再写进 `report_citation` 快照。没有 `[{type: table|bullets|quote|chart}]` 这类区块 schema。

不用结构化区块，原因有三：
- 用户可以自配 OpenAI 兼容的小模型。各家模型写 Markdown 都稳定，往工具参数里填嵌套的区块 JSON 却容易出错。
- 用户在源码编辑器里直接改、导出 `.md`、复制到别处，都不用转换。
- 追问时的局部修改用 `update_report` 的 `edits`（精确文本替换）就能做到，不需要区块 ID。

## Considered Options

- **结构化区块数组**：界面可以按类型做固定版式和图表，也可以按区块 ID 局部更新、按区块合并用户与 Agent 的修改。代价是工具 schema 复杂、模型容易出错，用户编辑需要区块编辑器，导出也要转换。被否。
- **Markdown 为主，另加 fenced JSON 的图表块**：MVP 不做图表，这个选项暂时用不上。日后要加图表，可以在本方案上增量引入，不必推翻本决定。

## Consequences

- 界面上没有固定版式，模板只能作为给 Agent 的写作提示。
- 用户与 Agent 的修改无法按区块自动合并，只能用整篇版本号做乐观并发，冲突时由用户选择保留哪一边。
- 引用标记是对 Agent 的契约，与 `v_*` 视图一样要保持兼容。已保存的报告里留着旧语法，日后改语法就要迁移正文。
