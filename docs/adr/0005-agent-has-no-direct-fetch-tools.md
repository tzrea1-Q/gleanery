# Agent 没有直接取数的工具，所有平台访问都经采集计划审批

Agent 的工具里没有 `search`、`collect_content` 这类直接访问平台的工具。这两种页面级操作只是采集执行器的内部步骤：采集计划的每个平台分段由执行器展开成这些步骤，在任务表队列里按平台串行执行。哪怕只想临时看一条内容，Agent 也要提一份只含"指定内容"的小计划，经 `start_collection` 审批（[ADR-0002](0002-plan-draft-and-approval-gate.md)）后才会执行。

原因：
- 每次平台访问都会用到用户的账号，并占用风控余量（冷却、锁定、每日额度）。地图已定的自主度基线是"采集前必须出计划并经用户确认"。
- 若让 Agent 自主调用单次搜索，就会绕过审批和数量上限，并在多轮推理中不知不觉累积请求。
- 页面驱动取数很慢（小红书每次 6–15 秒），同步工具调用会让 Agent 在对话里等上几分钟，与"Agent 从不等待采集"的执行模型冲突。

## Considered Options

- **开放只读的单次搜索 / 单条详情给 Agent 自主调用**（例如每次限 1 页）：Agent 更灵活，能边看边决定下一步采什么。代价是绕过审批与数量上限、风控责任落到模型身上，而且同步等待页面的结果拖慢对话。被否。
- **按 MediaCrawler 的接口粒度开放工具**（`list_comments(cursor)` 等）：评论 cursor 只在页面内部有效，页面驱动下做不到。被否。

## Consequences

- "先广撒网、再挑着补采"要分两份计划、审批两次：第一份只要摘要，第二份针对指定内容。计划卡片要让小计划的确认足够轻。
- Agent 对平台的了解只来自内容库与 `get_platform_status`。它不能"先搜搜看有多少结果"再起草计划，预计条数只能写成上限。
- 将来的定时监控也走同一条路径：监控规则是"计划模板 + 周期"，审批发生在创建规则时。
